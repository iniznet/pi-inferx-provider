# ⚡ pi-inferx-provider

**Open-weight models on [InferX](https://model.inferx.net) serverless inference endpoints**

_A [pi](https://github.com/earendil-works/pi-coding-agent) provider extension with reasoning, vision and per-token billing._

[![pi extension](https://img.shields.io/badge/pi-extension-blueviolet)](https://github.com/earendil-works/pi-coding-agent)
[![license](https://img.shields.io/badge/license-MIT-blue)](./LICENSE)

</div>

---

Access DeepSeek, GLM, Qwen, Gemma, GPT-OSS, Devstral and Agents-A1 endpoints through InferX's shared, token-billed OpenAI-compatible surface at `https://model.inferx.net/endpoints/v1`.

## Features

- **OpenAI-compatible API** - Uses InferX's `/endpoints/v1/chat/completions` endpoint
- **Reasoning models** - vLLM `--reasoning-parser` endpoints driven through `reasoning_effort`
- **Vision models** - Image input on the endpoints InferX publishes as multimodal
- **Tool use** - Function calling on every endpoint that publishes a tool-call parser
- **Streaming** - Real-time token streaming with `stream_options.include_usage`
- **Free tier** - Promotional endpoints billed at 100% off appear as **Free**
- **Stale-while-revalidate catalog** - the embedded catalog is what pi registers at load; a background refresh hot-swaps it when a key is configured
- **Delivered capability** - reasoning, vision and per-level thinking maps are curated from InferX's published vLLM Model Specs, not guessed from model names
- **Delisting grace** - an unpublished endpoint keeps serving saved sessions for 14 days

## Installation

### Option 1: Using `pi install` (Recommended)

```bash
pi install https://github.com/iniznet/pi-inferx-provider
```

Then set your API key and run pi:

```bash
# Recommended: add the key to auth.json (see Authentication below)
# Or set it as an environment variable
export INFERX_API_KEY=ix_your-api-key-here

pi
```

Create an inference key on the InferX dashboard under **Admin → Apikeys**.

### Option 2: Manual Clone

```bash
git clone https://github.com/iniznet/pi-inferx-provider.git
cd pi-inferx-provider
export INFERX_API_KEY=ix_your-api-key-here
pi -e /path/to/pi-inferx-provider
```

## Authentication

Resolved in this order:

1. **`auth.json`** (recommended) — add to `~/.pi/agent/auth.json`:
   ```json
   { "inferx": { "type": "api_key", "key": "ix_your-api-key" } }
   ```
   The `key` field accepts a literal value, an env-var reference, or a shell command (prefix
   `!`). See [pi's auth file docs](https://github.com/earendil-works/pi-coding-agent).
2. **Runtime override** — the `--api-key` CLI flag
3. **Environment variable** — `INFERX_API_KEY` (the name InferX publishes in its own setup snippets)

InferX keys are tenant-scoped (`ix_…`): the tenant is resolved from the key, so no tenant
header is ever sent by this extension.

## Environment Variables

| Variable | Required | Description |
|----------|----------|-------------|
| `INFERX_API_KEY` | Yes | Tenant inference key. pi only lists a provider's models once a credential resolves, so `/model` shows no `inferx` entries without one (the catalog itself still loads). |
| `INFERX_BASE_URL` | No | Override the shared surface with a dedicated per-tenant endpoint, e.g. `https://model.inferx.net/funccall/<tenant>/endpoints/<model>/v1` |

```
/model inferx glm-5.3-flash
```

### Reasoning

For reasoning endpoints, control thinking depth with `/reasoning` (or Shift+Tab). pi sends
`reasoning_effort`; each endpoint's accepted vocabulary is pinned in `patch.json`, and
levels an endpoint cannot honour are mapped to the nearest valid level so pi only ever
sends accepted values:

| Endpoint | Thinking levels exposed (pi) |
|---|---|
| `deepseek-v4-flash-0731`, `deepseek-v4-flash-vision-exp` | `off` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max` |
| `glm-5.3-flash` | `off` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max` |
| `qwen38-flash-next` | `off` / `low` / `medium` / `xhigh` |
| `Qwen3.6-35B-A3B-FP8` | `off` / `low` / `medium` / `high` |
| `Qwen3.8-27B-FP8` | `low` / `medium` |
| `gemma-4-31B-it-fp8` | `off` / `low` / `medium` / `high` |
| `Agents-A1`, `Devstral-2-…`, `gpt-oss-20b`, `Qwen3-Coder-Next-FP8` | no reasoning parser on this endpoint |

## Cold starts

InferX endpoints are serverless: every published Model Spec runs with `min_replica: 0`, so
an idle endpoint scales to zero and the first request pays a cold-start TTFT (InferX
publishes the measured value per endpoint). Expect the first turn after idle to be slow and
keep the session warm if latency matters. There is no key-authenticated endpoint to warn
from, so this extension does not attempt to pre-warm.

## API Compatibility

InferX serves stock vLLM images behind the OpenAI-compatible surface. pi auto-detects
compatibility settings from the base URL and has no rule for `model.inferx.net`, so the
request surface is pinned per model in `patch.json`. These pins were verified live against
`glm-5.3-flash`: vLLM here actually **tolerates** both max-token field names, `store`, and
the `developer` role (all return 200), so the pins are a deliberately minimal, universally
safe subset rather than an absolute requirement — the one place they genuinely matter is
`reasoning_effort`, where a value outside the parser's vocabulary is an error.

| Aspect | OpenAI default (auto-detected) | InferX |
|--------|-------------------------------|--------|
| Max tokens field | `max_completion_tokens` | `max_tokens` (InferX's own sample body; both accepted live) |
| `store` parameter | sent | omitted (accepted live, but unused by pi) |
| System prompt role | `developer` | `system` (accepted live either way; `system` maps to every chat template) |
| Thinking format | `openai` (`reasoning_content`) | `openai` ✅ matches the vLLM reasoning parsers |
| Reasoning effort | pi's level names | parser vocabulary only — levels outside it fail, so maps restrict to verified values |
| Tool choice | `strict` schemas | ✅ `--enable-auto-tool-choice` on tool-capable endpoints |
| `/v1/models` | public | 🔒 tenant-key gated (401 without a key) |
| Responses API | available | ❌ `/endpoints/v1/responses` returns 404 |

## Model catalog sync

```bash
npm run update-models   # optional: INFERX_API_KEY=ix_… for the authoritative listing
```

Two sources are folded together, because the authoritative one is key-gated:

1. `GET {INFERX_BASE_URL}/models` — the OpenAI-compatible listing, only when a key resolves
2. `GET https://model.inferx.net/catalog/endpoints` — the public endpoint table, which
   carries the case-sensitive slug, published context length and upstream owner

The script preserves curated data for known ids (a source only overwrites a field it
actually reports), moves delisted endpoints into `deprecated-models.json` for a 14-day grace
period, and rewrites the README table from `models.json → patch.json → custom-models.json`.

## Verified capability gaps

Recorded so nobody re-derives them:

- **No usage/credits status bar.** `pi-crofai-provider` shows a balance footer because
  `crof.ai/usage_api/` is key-authenticated. The equivalent InferX routes
  (`/endpoints/v1/{usage,account,credits,balance}`, `/endpoints/usage`, `/api/usage`) all
  return **404**, and the dashboard's tenant routes (`/generate_tenants`, `/proxy1/tenant/…`)
  redirect to `/login` because they are session-cookie authenticated, not `ix_`-key
  authenticated. Adding a status bar would mean inventing an endpoint.
- **`deepseek-v4-flash-0731` publishes no context length** (the catalog cell is an em dash).
  The value in `models.json` is curated from the upstream DeepSeek V4 Flash window, not read
  from InferX.
- **Vision on `glm-5.3-flash` and `qwen38-flash-next` is resolved and verified.** InferX
  publishes no Model Spec for either, but a majority of sibling provider catalogs and a live
  image-request probe against these endpoints confirm both accept and answer from image
  input (they described a solid-red test image). They are declared **image-capable** in
  `patch.json`.
- **`Agents-A1` is multimodal-adjacent but unverified.** Its Model Spec runs with
  `--mm-processor-cache-gb 0` and a live image probe did not trigger a "can't see" reply, yet
  it returned no clear colour answer — so it stays **text-only** until a focused probe
  settles it.
- **Capability flags are curated, not read.** InferX's `/models` listing is the bare OpenAI
  shape (`{data:[{id,object,created,owned_by}]}`) — no reasoning, modality, pricing or
  context — so `patch.json` carries them, derived from the published vLLM Model Specs
  (`--reasoning-parser`, `--tool-call-parser`, `apiType`), sibling provider E2E catalogs,
  and the live probes recorded in this extension's history. All six image-input models are
  live-verified;
  `gpt-oss-20b` is live-verified text-only (it answered "I can't see the image");
